# 전송 데이터와 큐, 혼잡제어

Zenoh 큐 크기와 TCP, UDP의 혼잡제어를 정하기 전에 무엇을 얼마나 보내는지 정리한다. 크기와 주기는 코드에서 읽은 값이고, PCD는 아직 코덱이 없어 시험 송신기의 값을 쓴다. 큐 크기는 이 문서의 표로 정하고 측정으로 확인한다. 측정 전의 값은 제안으로 표시한다.

## 1. 보내는 데이터

### 1.1 엣지에서 서버로 (상향)

| 데이터             | 한 번의 크기                                                                  | 주기          | 대역                    | 등급    | delivery | 지금 링크 | 늦으면                                          |
| ------------------ | ----------------------------------------------------------------------------- | ------------- | ----------------------- | ------- | -------- | --------- | ----------------------------------------------- |
| 앞 카메라 영상     | 몫 x 0.9 / 15. 150 kbit/s에서 1.1 KB, 2 Mbit/s에서 15 KB. keyframe은 그 몇 배 | 15 fps        | 135 kbit/s ~ 1.8 Mbit/s | teleop  | frame    | UDP       | 250 ms를 넘긴 프레임은 버리고 keyframe을 보낸다 |
| PCD                | 50 KB (시험값, 코덱 미정)                                                     | 2 Hz (시험값) | 약 400 kbit/s           | monitor | latest   | TCP       | 더 새 스캔이 오면 쓸모가 없다                   |
| odom, imu          | CDR 수백 B, zstd 압축                                                         | 2 Hz          | 수 kbit/s               | monitor | latest   | TCP       | 더 새 값이 오면 쓸모가 없다                     |
| diagnostics        | 메시지마다 다르다                                                             | 1 Hz          | 수 kbit/s               | monitor | reliable | TCP       | 순서대로 모두 남긴다                            |
| mux, e-stop 상태   | 수십 B                                                                        | 2 Hz          | 1 kbit/s 미만           | monitor | latest   | TCP       | 더 새 값이 오면 쓸모가 없다                     |

모든 데이터 조각에는 29 B 헤더(attachment)가 붙는다. 4 KB보다 큰 항목은 4 KB 조각으로 나뉜다. 링크 보고(`link/report`)와 몫(`link/budget`)은 차량 안의 router에서 끝나므로 상향 대역을 쓰지 않는다.

### 1.2 서버와 관제에서 엣지로 (하향)

| 데이터                     | 한 번의 크기 | 주기                    | 대역                | 지금 링크 | 잃으면                           |
| -------------------------- | ------------ | ----------------------- | ------------------- | --------- | -------------------------------- |
| 이동 명령(`motion`)        | 89 B         | 20 ms (50 Hz)           | 약 36 kbit/s        | UDP       | 다음 명령이 대신한다             |
| 무장, 정지, 비상정지, 해제 | 48 B         | 누를 때 한 번           | 무시할 만하다       | TCP       | 정지와 비상정지는 잃으면 안 된다 |
| 확인(`ack`)                | 16 B         | 받은 조각마다           | 영상 기준 수 kbit/s | TCP       | 지연 추정이 늦어진다             |
| keyframe 요청              | 수 B         | 영상 손실 뒤 200 ms마다 | 무시할 만하다       | TCP       | 다음 요청이 대신한다             |
| 원격 명령(`command`)       | 수십 B       | 누를 때                 | 무시할 만하다       | TCP       | 결과(`result`)가 오지 않는다     |

관제 프로그램은 이동 명령을 20 ms마다 보낸다(`MOTION_PERIOD`). teleop_control 설정의 주석은 20 Hz라고 적고 있어 코드와 다르다. watchdog 250 ms는 50 Hz에서 명령 12개를 놓친 시간이다.

### 1.3 우선순위와 혼잡 모드

| 보내는 쪽                                | Zenoh 우선순위  | express | 혼잡 모드 | 신뢰성      |
| ---------------------------------------- | --------------- | ------- | --------- | ----------- |
| 엣지의 teleop 제어(`state`, `hop`)       | RealTime        | 예      | Drop      | reliable    |
| 관제의 무장, 정지, 비상정지, 확인        | InteractiveHigh | 예      | Drop      | reliable    |
| 관제의 이동 명령                         | InteractiveHigh | 예      | Drop      | best effort |
| 영상 데이터                              | InteractiveHigh | 예      | Drop      | best effort |
| 엣지의 확인, keyframe 요청, 링크 보고    | InteractiveHigh | 예      | Drop      | reliable    |
| 엣지의 monitor 제어(`catalog`, `result`) | DataHigh        | 예      | Drop      | reliable    |
| monitor 데이터, reliable                 | Data            | 아니오  | Block     | reliable    |
| monitor 데이터, latest                   | Data            | 아니오  | Drop      | reliable    |

정지와 비상정지는 관제 쪽에서 InteractiveHigh로 나가므로, 엣지의 RealTime 제어보다 우선순위가 낮다. 영상 데이터와 같은 큐도 쓴다.

## 2. Zenoh 큐

### 2.1 구조

```
put() -> 우선순위별 큐(batch N개) -> 송신 스레드 -> OS 소켓 버퍼 -> 망
```

- 우선순위마다 batch가 N개 있다(`transport/link/tx/queue/size`, 기본 2). batch 하나의 크기는 `transport/link/tx/batch_size`다.
- 송신 스레드는 높은 우선순위의 batch부터 꺼내 소켓에 쓴다. 소켓 버퍼에 들어간 뒤에는 우선순위가 없다.
- express 메시지는 작아도 batch 하나를 혼자 쓴다.
- batch가 없으면 Drop 메시지는 1 ms(`wait_before_drop`) 기다린 뒤 버려진다. 버린 뒤에는 그 우선순위가 막힌 것으로 표시되고, 다음 Drop 메시지는 기다리지 않고 버려진다. 하나라도 들어가면 표시가 풀린다(`zenoh-transport` 1.10.1, `common/pipeline.rs`).
- Block 메시지는 batch가 날 때까지 `put()`에서 기다린다. 5초(`wait_before_close`)를 넘기면 세션을 닫는다.

### 2.2 지금 값

큐는 Zenoh 세션마다, 링크마다 있다. 데이터는 다음 세 곳의 큐를 차례로 지난다.

| 지점                                 | 설정                     | 우선순위마다 쌓이는 양 | 막히는 곳인가                       |
| ------------------------------------ | ------------------------ | ---------------------- | ----------------------------------- |
| 차량 프로그램(client) -> 엣지 router | 기본값(batch 64 KB, 2개) | 128 KB                 | 아니다. 같은 호스트라 바로 비워진다 |
| 엣지 router -> 서버 router (상향)    | batch 1400 B, 2개        | 2.8 KB                 | 그렇다. 셀룰러 상향                 |
| 서버 router -> 엣지 router (하향)    | batch 1400 B, 2개        | 2.8 KB                 | 그렇다. 셀룰러 하향                 |
| 관제 프로그램(router) -> 서버 router | batch 1400 B, 2개        | 2.8 KB                 | 관제의 망에 따라 다르다             |

`batch_size` 1400 B는 UDP 패킷이 IP 조각으로 나뉘지 않게 하려는 값이다(design.md 3.3). 이 값은 같은 세션의 TCP 링크에도 적용된다. 영상 조각 하나(4 KB)는 batch 3개를 쓰므로 큐에 한꺼번에 들어가지 못한다. 나머지 조각은 송신 스레드가 batch를 비워 줄 때까지 기다리고, Drop 메시지의 조각은 50 ms(`max_wait_before_drop_fragments`)를 넘기면 버려진다.

`zenoh_link.hpp`의 `kShortQueue`(batch 16 KB, 1개)는 어디에서도 쓰지 않는다.

### 2.3 크기를 정하는 기준

데이터를 쌓아 두는 곳은 tierlink의 Scheduler다. Scheduler는 늦은 영상 프레임과 옛 스캔을 버릴 수 있고, 몫에 맞춰 내보낸다. Zenoh 큐와 소켓 버퍼에 들어간 데이터는 버릴 수도, 앞질러 보낼 수도 없다. 그래서 Zenoh 큐는 다음 두 조건을 함께 만족하는 가장 작은 값으로 둔다.

1. 한 번에 들어오는 묶음을 버리지 않는다. 우선순위마다 한 번에 들어오는 가장 큰 묶음을 batch 수로 센다.
2. 큐가 찼을 때 기다리는 시간이 그 데이터의 지연 한도보다 짧다. 큐의 바이트 수를 링크 몫으로 나눈 값이 대기 시간이다.

| 우선순위        | 한 번에 들어오는 가장 큰 묶음                            | 조건 1의 batch 수      | 조건 2: 큐가 찼을 때 대기, 500 kbit/s 기준 | 제안 (측정 전) |
| --------------- | -------------------------------------------------------- | ---------------------- | ------------------------------------------ | -------------- |
| RealTime        | state 하나, hop 하나                                     | 2                      | 2 x 1400 B: 45 ms                          | 4              |
| InteractiveHigh | 영상 조각 하나(4 KB + 헤더), 확인 몇 개, 정지와 비상정지 | 3 (영상) + 3 (작은 것) | 6 x 1400 B: 134 ms                         | 6              |
| DataHigh        | catalog, result                                          | 2                      | 45 ms                                      | 2 (기본값)     |
| Data            | PCD 조각 하나(4 KB + 헤더)                               | 3                      | 67 ms                                      | 3              |

InteractiveHigh는 영상 조각과 정지가 같은 큐를 쓰므로 조건 1을 맞추면 조건 2가 길어진다. 정지와 비상정지를 다른 우선순위로 옮기면 이 큐를 영상 기준으로만 정할 수 있다. 이 표는 하향(서버에서 엣지)에도 같은 router 설정이 쓰인다는 가정이다.

## 3. TCP와 UDP의 혼잡제어

TCP 링크와 UDP 링크를 모두 구현하고 같은 조건에서 비교한다. 두 링크는 막힘을 드러내는 방식이 달라서, 링크 관리자의 혼잡제어도 링크마다 달라야 한다.

| 항목                    | TCP                                                                                               | UDP                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 혼잡제어                | 커널의 TCP(cubic 등)가 하고, 링크 관리자가 그 위에서 몫을 정한다                                  | 링크 관리자만 한다. Zenoh는 넣는 대로 보낸다                            |
| 잃은 패킷               | 커널이 다시 보낸다. 앱에는 지연으로만 보인다                                                      | 그대로 사라진다. 앱은 조각 번호의 빈칸으로 안다                         |
| 쌓이는 곳               | 커널 송신 버퍼(수백 KB에서 수 MB까지 자동으로 커진다), 그다음 망                                  | 망(모뎀, 기지국)과 소켓 버퍼(약 200 KB). 넘치면 버려진다                |
| 링크 관리자가 보는 신호 | 지연, 확인된 양. 손실은 보이지 않는다                                                             | 지연, 확인된 양, 손실률                                                 |
| 막힘을 아는 시점        | 송신 버퍼가 차고 난 뒤라 늦다. 버퍼를 줄이거나(`so_sndbuf`) 보낸 뒤 확인 안 된 양을 제한해야 한다 | 지연이 늘거나 손실이 생기면 바로 안다                                   |
| 내보내는 방식           | 커널이 창 크기만큼 몰아서 보낸다                                                                  | Scheduler가 몫에 맞춰 나눠 보내야 한다. 몰아서 보내면 소켓에서 버려진다 |
| 줄이는 기준             | 지연                                                                                              | 지연과 손실. 셀룰러의 무작위 손실은 막힘이 아니므로 둘을 구분해야 한다  |
| 다시 보내기             | 커널                                                                                              | 필요하면 앱이 조각 단위로. 더 새 항목이 생기면 포기한다                 |
| 앞을 막는 문제          | 한 연결 안에서 앞의 데이터가 늦으면 뒤가 모두 기다린다                                            | 없다                                                                    |

### 3.1 비교 방법

같은 데이터를 TCP만 쓰는 구성과 UDP만 쓰는 구성으로 보내고, design.md 5.1의 netem 프로파일을 그대로 쓴다.

| 프로파일           | 내용                              |

| tether, tether_bad | 실측 프로파일의 상향              |

| 지표             | 재는 방법                                                  |

| 영상 프레임 지연 | p50, p99, 최대                                             |
