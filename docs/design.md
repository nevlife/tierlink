# 서버와 엣지 설계

차량(엣지) 여러 대와 관제 PC가 서버 하나를 거쳐 원격조종 영상, 조종 명령, 텔레메트리를 주고받는 구성이다. 10대를 기준으로 잡는다. 서버의 데이터는 사람이 보는 화면에만 쓰고, 다른 시스템이 API로 가져가지 않는다.

## 1. 구성

```
차량 PC                                    서버
+-------------------------------+          +----------------------------------+
| teleop_video    --+           |   TCP    | zenohd (router): 중계만 한다       |
| teleop_control  --+--> 차량    |=========>|        ^ 127.0.0.1               |<====> 관제 PC
| fleet_telemetry --+    router |   UDP    | fleetd: ack, 저장, 조회, 차량 목록  |       관제 프로그램
+-------------------------------+          +----------------------------------+       (router 모드 세션)
```

| 구성 요소     | 하는 일                                                           | 언어와 도구                             |
| ------------- | ----------------------------------------------------------------- | --------------------------------------- |
| 차량 프로그램 | 영상 압축, 명령 검사, 텔레메트리 수집                             | C++17, ROS 2 Jazzy 컴포넌트, tierlink   |
| 차량 router   | 차량 안 프로그램의 연결을 모아 서버와 TCP, UDP 연결을 하나씩 연다 | Zenoh router 1.10.1                     |
| zenohd        | 메시지 중계. 인증서 검사와 접근 제어도 이후 여기서 한다           | Zenoh 공식 router 1.10.1, 설정 파일만   |
| fleetd        | monitor 등급의 ack, 차량별 MCAP 저장, 최근 기록 조회, 차량 목록   | Rust, zenoh crate (`server/`)           |
| 관제 프로그램 | 영상, 상태, 조종 입력                                             | Rust, egui (teleop_epoch의 `operator/`) |

중계(zenohd)와 저장(fleetd)을 다른 프로세스로 둔다. fleetd가 멈춰도 원격조종은 계속된다.

## 2. 프로토콜

| 층   | 선택                                                                                | 근거                                                                                                       |
| ---- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 전송 | TCP와 UDP를 함께 쓴다. UDP가 막힌 망에서는 TCP만 쓴다                               | 3절의 측정                                                                                                 |
| 중계 | Zenoh 1.10.1(차량, 서버, 관제 모두). 차량별 key는 `<prefix>/...`, 예: `scv/r01/...` | 같은 코드로 TCP, UDP, QUIC을 설정만 바꿔 고른다                                                            |
| 응용 | tierlink                                                                            | teleop 등급이 먼저 대역을 쓰고 monitor 등급이 남는 대역을 쓴다. 늦은 프레임을 버리고 비트레이트를 조절한다 |

조종의 안전 규칙(epoch, 순번, 유효 시간, watchdog, 비상정지 유지)은 응용 층과 차량에 있다. 전송을 바꿔도 그대로다.

## 3. 전송 선택

### 3.1 Zenoh가 메시지를 연결별로 나누는 조건

- endpoint 뒤의 `?rel=1`(꼭 가야 하는 메시지)과 `?rel=0`(다시 보내지 않는 메시지)으로 TCP와 UDP를 나눈다. `?prio=0-3`처럼 우선순위 범위로도 나눌 수 있다.
- **client 모드에서는 나뉘지 않는다.** client는 처음 연결된 endpoint 하나만 쓴다(`connect_peers(&peers, true)`, single link). 그래서 차량에는 router를 하나 두고 차량 프로그램은 그 router에 client로 붙는다. 관제 프로그램은 자기 세션을 router 모드로 연다.
- peer 모드는 두 연결을 열지만, peer 둘 사이의 데이터가 router를 거쳐 전달되지 않았다.
- 메시지 하나가 어느 연결로 갈지는 publisher의 reliability가 정한다. zenoh-c에서는 `Z_FEATURE_UNSTABLE_API` 아래에 있고, 우리가 빌드에 쓰는 zenoh_cpp_vendor는 이 기능을 켜고 빌드돼 있다.
- 위 동작은 1.6.2에서 확인했고, 1.10.1에서 client 모드가 UDP를 쓰지 않는 것과 router 모드가 영상을 UDP로 보내는 것을 다시 확인했다.
- **UDP 묶음 크기를 1400 B로 제한한다**(`transport/link/tx/batch_size`). 리눅스에서 Zenoh의 UDP 묶음 크기는 기본 64 KB다. 그러면 8 KB 프레임 하나가 IP 조각 여러 개로 나뉘고, 조각 하나만 잃어도 프레임 전체를 잃는다. 제한하기 전에는 깨끗한 경로에서 프레임을 2~5% 잃었고, 제한한 뒤에는 1% 안팎을 잃었다.

### 3.2 측정

- 영상과 비슷한 부하: 15 fps, 프레임 8.3 KB, 4초마다 40 KB keyframe. 약 1 Mbit/s다.
- 조종: 20 Hz, 100 B.
- 경로: 보내는 쪽(컨테이너) → 인터넷 → 서버 router → 받는 쪽.
- 보내는 쪽 컨테이너의 송신 인터페이스에 netem을 걸었다. 망 프로파일은 teleop_epoch의 `tmp/teleop_lab/profiles`에서 `up` 줄만 가져왔다. 보내는 쪽과 받는 쪽이 같은 커널 시계를 쓰므로 지연은 한쪽 방향 값이다.
- 각 조건은 60초씩 1회 측정했다. 따로 표시한 경우만 반복했다. 이 표는 Zenoh 1.6.2로 측정했다.

| 망                                          | 방식                         | 영상 손실 | 영상 지연 p99 / 최대  | 200 ms 넘은 영상 | 조종 지연 p99 / 최대                     |
| ------------------------------------------- | ---------------------------- | --------- | --------------------- | ---------------- | ---------------------------------------- |
| 깨끗함                                      | TCP                          | 0%        | 18 / 86 ms            | 0%               | 15 / 77 ms                               |
| 깨끗함                                      | TCP + UDP(1400 B)            | 1.0~1.3%  | 14~16 / 24~33 ms      | 0%               | 16~17 / 20~75 ms                         |
| tether: 3초마다 약 0.2초 멈춤               | TCP                          | 0%        | 390 / 498 ms          | 4.5%             | 393 / 528 ms                             |
| tether                                      | TCP + UDP                    | 1.1%      | 368 / 499 ms          | 3.6%             | 383 / 512 ms                             |
| tether_bad: 더 잦은 멈춤, 30초마다 1초 끊김 | TCP                          | 10.8%     | 585 / 951 ms          | 11.7%            | 602 / 987 ms                             |
| tether_bad                                  | TCP + UDP                    | 14.8%     | 525 / 707 ms          | 8.2%             | 518 / 710 ms                             |
| 무작위 손실 2%, 30 ms                       | TCP                          | 0%        | 430 / 609 ms          | 2.6%             | 402 / 598 ms                             |
| 무작위 손실 2%                              | TCP 둘(우선순위로 나눔), 2회 | 0%        | 318~972 / 461~1097 ms | 2.6~5.2%         | 299~957 / 455~1088 ms                    |
| 무작위 손실 2%                              | TCP + UDP                    | 11.6%     | 51 / 62 ms            | 0%               | 136 / 153 ms                             |
| 무작위 손실 2%                              | TCP + UDP, 조종도 UDP        | 13.8%     | 48 / 50 ms            | 0%               | 47 / 48 ms (손실 1.4%, 최장 공백 107 ms) |

tether_bad의 TCP 손실은 망에서 사라진 것이 아니다. 송신 대기열이 차서 Zenoh가 버린 것이다(`CongestionControl::Drop`).

### 3.3 결정

- **영상은 UDP로 보낸다.** 무작위 손실에서 TCP는 재전송을 기다리느라 p99가 0.4~1초까지 올라갔다. UDP는 50 ms 안팎을 유지했다. 대신 프레임 손실이 생긴다. 8 KB 프레임은 패킷 6개라서, 패킷 손실 2%가 프레임 손실 약 11%가 된다(1 - 0.98^6). 이 손실을 다루는 방법은 5절에 있다.
- **이동 명령(motion)도 UDP로 보낸다.** 20 Hz로 계속 보내고 순번으로 늦은 것을 버리므로, 하나를 잃어도 50 ms 뒤 다음 명령이 대신한다. 측정한 최장 공백 107 ms는 차량의 watchdog 250 ms 안에 있다.
- **무장, 정지, 비상정지, 해제, 상태, 텔레메트리는 TCP로 보낸다.** 반드시 도착해야 하기 때문이다.
- 멈춤(stall)이 많은 망에서는 어느 방식이든 멈춘 시간만큼 늦는다. 이 경우의 대응은 차량이 서는 것(watchdog, 영상 공백 시 관제의 조종 해제)이다.
- TCP 연결을 우선순위로 나눠도 무작위 손실에서는 나아지지 않았다. 조종 연결도 같은 손실을 겪고 재전송을 기다리기 때문이다.

## 4. 서버

### 4.1 배포

`deploy/server/`의 docker compose로 zenohd와 fleetd를 함께 올린다.

```bash
cd deploy/server
cp env.example .env              # 공개 포트(TCP, UDP), fleetd용 로컬 포트, 경로
cp fleetd.example.yaml fleetd.yaml   # 차량 목록
docker compose up -d --build
```

- `.env`, `fleetd.yaml`, `data/`는 서버에만 둔다(`.gitignore`). 서버 주소와 포트는 저장소에 넣지 않는다.
- zenohd는 공개 TCP와 UDP 포트 외에 `127.0.0.1`의 포트를 하나 더 연다. fleetd는 이 포트로 붙는다.
- zenohd 설정(`zenohd.json5`)의 값은 다음과 같다. `max_links` 4는 차량 router가 TCP와 UDP를 함께 열 수 있게 하는 값이다. lease 1000 ms와 keep_alive 4는 tierlink의 `make_config`와 같다. 묶음 크기는 1400 B다.

### 4.2 fleetd

| 기능      | 동작                                                                                                                                                                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ack       | `<prefix>/monitor/data/*`의 메시지마다 `<prefix>/monitor/ack`로 ack를 보낸다. 차량의 monitor 조절기는 이 ack로 전송 속도를 정한다. 관제 프로그램은 monitor를 ack하지 않는다(`--ack-monitor`는 fleetd 없이 시험할 때 쓴다)                                     |
| 저장      | 차량별 폴더에 UTC 한 시간마다 MCAP 파일 하나(`<data>/<id>/YYYYMMDD-HH.mcap`)를 만든다. 채널은 차량의 ROS 토픽 이름, 메시지는 CDR, schema에는 타입 이름만 적는다. 그래서 `ros2 bag play`로 읽는다. 같은 시간에 다시 시작하면 `_2`를 붙여 앞 파일을 덮지 않는다 |
| 최근 기록 | `<prefix>/history/<stream>?seconds=N`에 답한다. 답 하나에 메시지마다 받은 시각(Unix ns, u64 LE), CDR 길이(u32 LE), CDR을 이어 붙인다. 메모리에 `history_seconds`만큼 둔다                                                                                     |
| 차량 목록 | `fleet/vehicles`에 JSON으로 답한다. 차량 ID, prefix, 차종, 지금 살아 있는 프로세스(`<prefix>/alive/*` 토큰)가 들어간다                                                                                                                                        |

- 타입을 모르는 스트림(catalog가 오기 전의 메시지)은 저장하지 않고, 종료할 때 개수를 로그에 남긴다.
- MCAP의 색인은 파일을 닫을 때 쓴다. fleetd는 SIGTERM을 받으면 파일을 닫고 끝난다(`docker compose stop`). 강제로 죽으면 그 시간의 파일에 색인이 없다.
- 데이터베이스는 쓰지 않는다. 외부 API가 없고 10대 규모라서, 차량 여러 대를 묶어 묻는 질의가 없다.

## 5. 엣지(차량)

- 차량 router는 `tierlink_edge`다. 차량 프로그램은 `tcp/127.0.0.1:7447`로 붙고, `tierlink_edge`가 서버와 `tcp/...?rel=1`, `udp/...?rel=0` 두 연결을 연다. UDP가 막힌 망에서는 UDP endpoint를 빼서 TCP만 쓴다.
- `tierlink_edge`는 링크 관리자도 겸한다. 차량의 Uplink가 100 ms마다 보낸 양, ack된 양, 지연을 `<prefix>/link/report/<tier>`로 보고한다. 링크 관리자는 이 보고로 차량 전체의 대역을 하나로 추정하고, 등급별 몫을 `<prefix>/link/budget/<tier>`로 100 ms마다 공지한다.

| 규칙               | 동작                                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 줄이기             | 지연이 100 ms를 넘으면, 실제로 ack된 양의 0.85배로 줄인다. 300 ms에 한 번까지                                                                                                         |
| 늘리기             | 지연이 30 ms 아래로 1초 이어지고, 보낸 양이 대역의 80% 이상일 때만 늘린다. 100 kbit/s와 지금 대역의 10% 중 큰 값만큼 늘린다. 쓰지 않는 대역은 늘리지 않는다                           |
| teleop 몫          | 대역에서 monitor 최소 몫(30 kbit/s)을 뺀 값을 150 kbit/s~2 Mbit/s로 자른다                                                                                                            |
| monitor 몫         | 나머지. teleop이 돌고 지연이 50 ms를 넘으면 최소 몫만 받는다. teleop이 없으면 대역 전체를 받는다                                                                                      |
| 계산에서 빼는 등급 | 3초 안에 ack가 한 번도 없었던 등급. 보는 관제가 없는 영상은 ack가 없어서 정지(stall)가 계속 커지는데, 이것을 혼잡으로 읽지 않기 위해서다. ack가 오다가 끊긴 것은 끊김으로 보고 줄인다 |
| 몫이 끊기면        | 각 프로그램은 500 ms 동안 몫을 못 받으면 자기 조절기(AIMD)로 돌아간다                                                                                                                 |

- 예전 방식(teleop_video가 텔레메트리 몫을 알려 주던 allowance)은 이것으로 대체했다.
- 4 KB보다 큰 메시지(PCD, keyframe)는 4 KB 조각으로 나눠 몫에 맞춰 조금씩 보낸다. 조각 사이로 영상 프레임이 먼저 나간다. 데이터 헤더에 조각 번호와 조각 수가 들어가서 헤더가 25 B에서 29 B가 됐다. 받는 쪽(tierlink `Receiver`, fleetd, 관제 프로그램)은 조각을 다시 합친다. 새 메시지의 조각이 오면 아직 다 모이지 않은 이전 메시지는 버린다.

### 5.1 대역 변화 측정

보내는 쪽(`tierlink_edge`와 시험 송신기)을 netem 컨테이너에 두고, 상향 대역을 20초마다 3 -> 1 -> 0.5 Mbit/s로 바꾼 뒤 다시 3 Mbit/s로 돌렸다(지연 30 ms, netem 대기열 100 패킷). 프로파일에는 마지막에 2 Mbit/s 단계가 있었지만, 프로파일을 되풀이하는 스크립트가 그 단계를 곧바로 첫 줄(3 Mbit/s)로 덮어썼다. 영상은 몫의 90%로 15 fps를 보내고, PCD와 같은 50 KB 메시지를 1초에 2번 monitor 등급으로 보냈다.

| 구간                                | 조각 나누기 전      | 조각 나누기와 10% 늘리기 뒤 |
| ----------------------------------- | ------------------- | --------------------------- |
| 3 -> 1 Mbit/s 직후 영상 지연 최대   | 475 ms              | 259 ms                      |
| 1 -> 0.5 Mbit/s 직후 영상 지연 최대 | 879 ms (PCD와 겹침) | 315 ms                      |
| PCD 메시지가 나갈 때 영상 지연      | 0.7~0.9초로 튐      | 75~105 ms, 튀지 않음        |
| 0.5 -> 3 Mbit/s 뒤 1.8 Mbit/s 회복  | 15초                | 12초                        |
| 대역이 유지될 때 영상 지연          | 60~100 ms           | 60~105 ms                   |

- teleop이 도는 동안 PCD는 monitor 최소 몫(30 kbit/s)만 받아서, 50 KB 메시지 하나가 11~13초 걸려 도착했다. 영상이 대역을 거의 다 가져가기 때문이다.
- teleop_video의 영상 publisher와 관제 프로그램의 이동 명령(`motion`)은 best effort로 둔다. 나머지 제어 key(무장, 정지, 비상정지, 해제, 상태)는 reliable로 둔다.
- UDP에서 잃는 프레임은 XOR FEC로 다룬다(5.4). intra refresh는 GStreamer의 NVENC 요소(`nvcudah265enc`)에 속성이 없어서 x265에서만 쓸 수 있다.

### 5.2 SCReAM과 비교

SCReAM(Ericsson의 RTP 영상 혼잡제어, RFC 8298)의 대역 시험 도구를 같은 netem 단계에 걸었다. 이번에는 마지막 단계도 2 Mbit/s로 20초 유지했고, tierlink도 같은 프로파일로 다시 쟀다. SCReAM은 15 fps, 150~4000 kbit/s로 두었다.

| 구간                                      | SCReAM            | tierlink          |
| ----------------------------------------- | ----------------- | ----------------- |
| 3 Mbit/s, 마지막 10초 전송률              | 2662 kbit/s (89%) | 1353 kbit/s (45%) |
| 1 Mbit/s, 마지막 10초 전송률              | 497 kbit/s (50%)  | 569 kbit/s (57%)  |
| 0.5 Mbit/s, 마지막 10초 전송률            | 418 kbit/s (84%)  | 274 kbit/s (55%)  |
| 2 Mbit/s, 마지막 10초 전송률              | 1857 kbit/s (93%) | 1123 kbit/s (56%) |
| 3 -> 1 Mbit/s 직후 지연 최대              | 275 ms            | 333 ms            |
| 1 -> 0.5 Mbit/s 직후 지연 최대            | 111 ms            | 341 ms            |
| 시작 뒤 2.7 Mbit/s에 닿는 시간            | 14초              | 20초 안에 못 닿음 |
| 0.5 -> 2 Mbit/s 뒤 1.8 Mbit/s에 닿는 시간 | 10초              | 20초 안에 못 닿음 |

지연은 그 측정에서 가장 낮은 지연 위로 더해진 값이다. 두 측정은 조건이 다르다.

- SCReAM은 패킷마다 잰 망 지연의 최대다. 보내는 쪽 대기열에서 기다린 시간은 들지 않는다. SCReAM은 그 대기열이 0.2초를 넘으면 비우는데, 3 -> 1 Mbit/s 때 43 패킷(약 52 KB)을 한 번 버렸다.
- tierlink는 프레임 지연의 1초 평균 가운데 최대다. 보내는 쪽 대기열에서 기다린 시간이 들고, 1초 평균이라 순간 최대는 더 높다. 이전 측정(5.1)의 259 ms, 315 ms보다 높게 나왔다.
- SCReAM은 같은 호스트의 컨테이너 사이로 영상만 보냈다. tierlink는 서버 router를 거쳤고 PCD도 함께 보냈다.

SCReAM이 대역을 더 많이 쓰는 까닭은 늘리는 속도다. SCReAM은 패킷마다 오는 확인으로 지연이 낮은 동안 창(congestion window)을 곱으로 늘리고, 마지막으로 막혔던 수준에 가까워지면 천천히 늘린다. tierlink는 1초마다 10%씩 늘린다. 대역이 줄 때 지연이 덜 튀는 것도 같은 까닭이다. 확인이 패킷마다 오니 막힌 것을 1초 단위 보고보다 먼저 안다. 1 Mbit/s 구간에서는 SCReAM도 크게 줄인 뒤 천천히 늘려서 대역의 절반만 썼다.

3 Mbit/s 구간의 45%에는 몫의 상한도 들어 있다. teleop 몫은 2 Mbit/s(`teleop_max_bps`)에서 멈추고 영상은 그 90%를 쓰므로, 영상만으로는 3 Mbit/s의 60%를 넘지 못한다. 남는 몫은 monitor로 가는데 시험 송신기의 PCD는 0.4 Mbit/s만 보낸다.

SCReAM처럼 늘리는 규칙도 시험했다. 막혔을 때 전달된 양의 90% 아래에서는 25%씩, 그 위에서는 100 kbit/s씩, 넘어서면 10%씩 늘렸다. 같은 프로파일로 이전 규칙(A)과 번갈아 세 번씩 쟀다(대역 대비 영상 전송률, 세 번 평균).

| 구간       | A   | B   |
| ---------- | --- | --- |
| 3 Mbit/s   | 45% | 51% |
| 1 Mbit/s   | 56% | 59% |
| 0.5 Mbit/s | 67% | 56% |
| 2 Mbit/s   | 60% | 50% |

나아지지 않아서 넣지 않았다. 링크 관리자 로그를 보면 B도 1525 kbit/s에서 7초 동안 늘리지 못했다. 늘리려면 지연이 1초 내내 30 ms 아래여야 하는데, 프레임이 지날 때 지연이 잠깐 30 ms를 넘으면 1초를 처음부터 다시 센다. 그래서 늘리는 폭보다 늘릴 기회가 적은 것이 먼저다. 30~100 ms 사이에서 다시 세지 않게 바꾸자 한 번의 측정에서 2 Mbit/s 구간이 80%가 됐지만, 3 Mbit/s에서 대역을 3.7 Mbit/s로 넘겨 잡아 3 -> 1 Mbit/s 직후 지연이 699 ms까지 올랐다. SCReAM과의 차이는 늘리는 규칙보다 확인의 간격(패킷마다와 100 ms 보고)에 있다고 본다.

### 5.3 전송 방식별 혼잡제어: GCC와 LEDBAT

측정 도구(`tools/bench`)를 만들어 서버도 로컬 컨테이너에 두었다. 같은 빌드, 같은 프로파일로 두 추정 방식을 번갈아 쟀다. 측정 송신기는 영상(15 fps, 몫의 90%에서 패리티 몫을 뺀 값), PCD 크기의 50 KB 메시지(2 Hz), 텔레메트리(200 B, 10 Hz), 무장 상태(60 B, 10 Hz)를 보낸다.

| 추정 방식 | 줄이는 신호                                                                                                    | 늘리는 규칙                                                               |
| --------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `aimd`    | 지연이 100 ms를 넘는다                                                                                         | 지연이 30 ms 아래로 1초 이어지면 10%                                      |
| `gcc`     | trendline(도착 간격과 보낸 간격의 차이를 쌓아 직선으로 맞춘 기울기)이 과사용을 보이거나 지연이 100 ms를 넘는다 | 정상이면 초당 8%, 마지막 과사용 근처에서는 초당 60 kbit/s(또는 20 kbit/s) |

대역 단계(3 -> 1 -> 0.5 -> 2 Mbit/s, 20초씩), FEC 켬, 각 두 번이다. 전송률은 패리티를 뺀 영상 전송률을 netem 대역으로 나눈 값이다.

| 지표                             | aimd               | gcc, 60 kbit/s     | gcc, 20 kbit/s     |
| -------------------------------- | ------------------ | ------------------ | ------------------ |
| 영상 지연 p50                    | 60~61 ms           | 64~65 ms           | 57~59 ms           |
| 영상 지연 p95                    | 107~108 ms         | 242~269 ms         | 180~204 ms         |
| 영상 지연 최대                   | 288~289 ms         | 496~507 ms         | 488~526 ms         |
| 무장 상태 지연 p99               | 212~238 ms         | 430~480 ms         | 400~423 ms         |
| 1 Mbit/s 구간 전송률, 지연 p95   | 38~45%, 146~209 ms | 51%, 414~422 ms    | 55~58%, 421~440 ms |
| 0.5 Mbit/s 구간 전송률, 지연 p95 | 36~37%, 133~212 ms | 40~41%, 323~370 ms | 42~44%, 228~308 ms |

- LTE 핸드오버 프로파일(8 Mbit/s, 15초마다 400 ms 끊김과 3초 대역 저하, 60초, 두 번)에서도 같았다. 영상 지연 p95가 aimd 116~146 ms, gcc 216~330 ms였다. 끊김마다 프레임을 잃은 것은 둘 다 6개였다. 400 ms 끊김은 FEC로 되살릴 수 없다.
- GCC는 대역을 10~15%p 더 썼지만 지연이 두 배가 됐다. 그래서 기본값은 `aimd`로 두고, GCC는 `edge.estimator`로 고를 수 있게만 둔다.
- 늦게 잡는 까닭은 신호의 수다. libwebrtc는 패킷을 고르게 내보내서 기울기 점이 초당 수백 개 생긴다. 여기서는 한 프레임의 조각이 같은 5 ms 안에 나가서 프레임 하나가 점 하나라, 초당 15개뿐이다. 창 20개를 채우는 데 1.3초가 걸린다.
- 정상 상태에서도 계속 늘리는 것도 까닭이다. AIMD는 1초 동안 지연이 낮아야 늘리지만, GCC는 기울기가 0 근처이면 늘린다. 그래서 큐가 반복해서 쌓인다.
- 조각을 프레임 안에서 고르게 내보내 점을 늘리거나 창을 줄이는 것은 다음에 잰다.

monitor 등급의 자기 조절기를 LEDBAT(RFC 6817, 목표 지연 25 ms)로 바꾼 측정에서는 차이가 없었다. teleop이 도는 동안 monitor는 최소 몫(30 kbit/s)만 받아서 망 큐를 거의 쓰지 않기 때문이다. teleop 없이 PCD를 많이 보내는 경우에 다시 잰다.

### 5.4 UDP 영상 손실과 FEC

영상 조각을 1200 B로 줄여 Zenoh 헤더(캡처에서 83 B)를 더해도 UDP 데이터그램 하나(batch 1400 B)에 들어가게 했다. Zenoh는 여러 데이터그램으로 나뉜 메시지를 조각 하나만 잃어도 통째로 버리기 때문이다. 조각 4개마다 XOR 패리티 조각 하나를 붙이고, 받는 쪽은 그룹마다 잃은 조각 하나를 되살린다. 데이터 헤더는 FEC 그룹 크기 1 B가 더해져 30 B가 됐다.

인코더 목표는 몫에서 패리티 몫을 뺀 값이다(`Uplink::parity_ratio`). 처음에는 빼지 않아서 영상이 몫을 25~33% 넘었다. 그러자 송신 대기열에서 프레임이 250 ms를 넘겨 버려졌고, 15초에 keyframe이 17번 나왔다.

2% 무작위 손실(30 ms, 3 Mbit/s), 30초, 두 번씩이다.

| 지표          | FEC 4      | FEC 없음   |
| ------------- | ---------- | ---------- |
| 영상 지연 p50 | 59~61 ms   | 271~275 ms |
| 영상 지연 p95 | 101~138 ms | 316~321 ms |
| 잃은 프레임   | 1~6        | 87~88      |
| keyframe      | 2~7        | 25         |
| 되살린 조각   | 38~52      | 0          |

FEC가 없으면 손실마다 keyframe을 요청하고, 평소 프레임의 4배인 keyframe이 송신 대기열을 막아 지연이 4배가 된다. 대역 단계에서도 대역이 줄 때 netem 대기열에서 버려진 조각 62~264개를 되살려 잃은 프레임이 없었다.

### 5.5 PCD(라이다)

차량의 텔레메트리 프로그램이 VLP-32C 스캔을 거리 표로 바꿔 8구간으로 나눠 보낸다. 녹화한 스캔 50개로 스캔당 57.4 KB(반사 세기 4비트), 오차 중앙값 0.40 cm, p99 0.82 cm였다. 구간은 따로 풀리므로 `transport: udp`로 UDP에 실을 수 있다. 이때 영상과 같은 1200 B 조각과 FEC를 쓴다. fleetd는 이 스트림을 받은 그대로 MCAP에 적는다.
