# 서버와 엣지 설계

차량(엣지) 여러 대와 관제 PC가 서버 하나를 거쳐 원격조종 영상, 조종 명령, 텔레메트리를 주고받는 구성이다. 10대를 기준으로 잡는다. 서버의 데이터는 사람이 보는 화면에만 쓰고, 다른 시스템이 API로 가져가지 않는다.

## 1. 구성

```
차량 PC                                    서버
+-------------------------------+          +----------------------------------+
| teleop_video    --+           |   TCP    | zenohd (router): 중계만 한다       |
| teleop_control  --+--> 차량    |=========>|        ^ 127.0.0.1               |<====> 관제 PC
| fleet_telemetry --+    router |   UDP    | fleetd: ack, 저장, 조회, 차량 목록  |       관제 프로그램
+-------------------------------+          +----------------------------------+       (router 모드 세션)
```

| 구성 요소     | 하는 일                                                           | 언어와 도구                             |
| ------------- | ----------------------------------------------------------------- | --------------------------------------- |
| 차량 프로그램 | 영상 압축, 명령 검사, 텔레메트리 수집                             | C++17, ROS 2 Jazzy 컴포넌트, tierlink   |
| 차량 router   | 차량 안 프로그램의 연결을 모아 서버와 TCP, UDP 연결을 하나씩 연다 | Zenoh router 1.10.1                     |
| zenohd        | 메시지 중계. 인증서 검사와 접근 제어도 이후 여기서 한다           | Zenoh 공식 router 1.10.1, 설정 파일만   |
| fleetd        | monitor 등급의 ack, 차량별 MCAP 저장, 최근 기록 조회, 차량 목록   | Rust, zenoh crate (`server/`)           |
| 관제 프로그램 | 영상, 상태, 조종 입력                                             | Rust, egui (teleop_epoch의 `operator/`) |

중계(zenohd)와 저장(fleetd)을 다른 프로세스로 둔다. fleetd가 멈춰도 원격조종은 계속된다.

## 2. 프로토콜

| 층   | 선택                                                                                | 근거                                                                                                       |
| ---- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 전송 | TCP와 UDP를 함께 쓴다. UDP가 막힌 망에서는 TCP만 쓴다                               | 3절의 측정                                                                                                 |
| 중계 | Zenoh 1.10.1(차량, 서버, 관제 모두). 차량별 key는 `<prefix>/...`, 예: `scv/r01/...` | 같은 코드로 TCP, UDP, QUIC을 설정만 바꿔 고른다                                                            |
| 응용 | tierlink                                                                            | teleop 등급이 먼저 대역을 쓰고 monitor 등급이 남는 대역을 쓴다. 늦은 프레임을 버리고 비트레이트를 조절한다 |

조종의 안전 규칙(epoch, 순번, 유효 시간, watchdog, 비상정지 유지)은 응용 층과 차량에 있다. 전송을 바꿔도 그대로다.

## 3. 전송 선택

### 3.1 Zenoh가 메시지를 연결별로 나누는 조건

- endpoint 뒤의 `?rel=1`(꼭 가야 하는 메시지)과 `?rel=0`(다시 보내지 않는 메시지)으로 TCP와 UDP를 나눈다. `?prio=0-3`처럼 우선순위 범위로도 나눌 수 있다.
- **client 모드에서는 나뉘지 않는다.** client는 처음 연결된 endpoint 하나만 쓴다(`connect_peers(&peers, true)`, single link). 그래서 차량에는 router를 하나 두고 차량 프로그램은 그 router에 client로 붙는다. 관제 프로그램은 자기 세션을 router 모드로 연다.
- peer 모드는 두 연결을 열지만, peer 둘 사이의 데이터가 router를 거쳐 전달되지 않았다.
- 메시지 하나가 어느 연결로 갈지는 publisher의 reliability가 정한다. zenoh-c에서는 `Z_FEATURE_UNSTABLE_API` 아래에 있고, 우리가 빌드에 쓰는 zenoh_cpp_vendor는 이 기능을 켜고 빌드돼 있다.
- 위 동작은 1.6.2에서 확인했고, 1.10.1에서 client 모드가 UDP를 쓰지 않는 것과 router 모드가 영상을 UDP로 보내는 것을 다시 확인했다.
- **UDP 묶음 크기를 1400 B로 제한한다**(`transport/link/tx/batch_size`). 리눅스에서 Zenoh의 UDP 묶음 크기는 기본 64 KB다. 그러면 8 KB 프레임 하나가 IP 조각 여러 개로 나뉘고, 조각 하나만 잃어도 프레임 전체를 잃는다. 제한하기 전에는 깨끗한 경로에서 프레임을 2~5% 잃었고, 제한한 뒤에는 1% 안팎을 잃었다.

### 3.2 측정

- 영상과 비슷한 부하: 15 fps, 프레임 8.3 KB, 4초마다 40 KB keyframe. 약 1 Mbit/s다.
- 조종: 20 Hz, 100 B.
- 경로: 보내는 쪽(컨테이너) → 인터넷 → 서버 router → 받는 쪽.
- 보내는 쪽 컨테이너의 송신 인터페이스에 netem을 걸었다. 망 프로파일은 teleop_epoch의 `tmp/teleop_lab/profiles`에서 `up` 줄만 가져왔다. 보내는 쪽과 받는 쪽이 같은 커널 시계를 쓰므로 지연은 한쪽 방향 값이다.
- 각 조건은 60초씩 1회 측정했다. 따로 표시한 경우만 반복했다. 이 표는 Zenoh 1.6.2로 측정했다.

| 망                                          | 방식                         | 영상 손실 | 영상 지연 p99 / 최대  | 200 ms 넘은 영상 | 조종 지연 p99 / 최대                     |
| ------------------------------------------- | ---------------------------- | --------- | --------------------- | ---------------- | ---------------------------------------- |
| 깨끗함                                      | TCP                          | 0%        | 18 / 86 ms            | 0%               | 15 / 77 ms                               |
| 깨끗함                                      | TCP + UDP(1400 B)            | 1.0~1.3%  | 14~16 / 24~33 ms      | 0%               | 16~17 / 20~75 ms                         |
| tether: 3초마다 약 0.2초 멈춤               | TCP                          | 0%        | 390 / 498 ms          | 4.5%             | 393 / 528 ms                             |
| tether                                      | TCP + UDP                    | 1.1%      | 368 / 499 ms          | 3.6%             | 383 / 512 ms                             |
| tether_bad: 더 잦은 멈춤, 30초마다 1초 끊김 | TCP                          | 10.8%     | 585 / 951 ms          | 11.7%            | 602 / 987 ms                             |
| tether_bad                                  | TCP + UDP                    | 14.8%     | 525 / 707 ms          | 8.2%             | 518 / 710 ms                             |
| 무작위 손실 2%, 30 ms                       | TCP                          | 0%        | 430 / 609 ms          | 2.6%             | 402 / 598 ms                             |
| 무작위 손실 2%                              | TCP 둘(우선순위로 나눔), 2회 | 0%        | 318~972 / 461~1097 ms | 2.6~5.2%         | 299~957 / 455~1088 ms                    |
| 무작위 손실 2%                              | TCP + UDP                    | 11.6%     | 51 / 62 ms            | 0%               | 136 / 153 ms                             |
| 무작위 손실 2%                              | TCP + UDP, 조종도 UDP        | 13.8%     | 48 / 50 ms            | 0%               | 47 / 48 ms (손실 1.4%, 최장 공백 107 ms) |

tether_bad의 TCP 손실은 망에서 사라진 것이 아니다. 송신 대기열이 차서 Zenoh가 버린 것이다(`CongestionControl::Drop`).

### 3.3 결정

- **영상은 UDP로 보낸다.** 무작위 손실에서 TCP는 재전송을 기다리느라 p99가 0.4~1초까지 올라갔다. UDP는 50 ms 안팎을 유지했다. 대신 프레임 손실이 생긴다. 8 KB 프레임은 패킷 6개라서, 패킷 손실 2%가 프레임 손실 약 11%가 된다(1 - 0.98^6). 이 손실을 다루는 방법은 5절에 있다.
- **이동 명령(motion)도 UDP로 보낸다.** 20 Hz로 계속 보내고 순번으로 늦은 것을 버리므로, 하나를 잃어도 50 ms 뒤 다음 명령이 대신한다. 측정한 최장 공백 107 ms는 차량의 watchdog 250 ms 안에 있다.
- **무장, 정지, 비상정지, 해제, 상태, 텔레메트리는 TCP로 보낸다.** 반드시 도착해야 하기 때문이다.
- 멈춤(stall)이 많은 망에서는 어느 방식이든 멈춘 시간만큼 늦는다. 이 경우의 대응은 차량이 서는 것(watchdog, 영상 공백 시 관제의 조종 해제)이다.
- TCP 연결을 우선순위로 나눠도 무작위 손실에서는 나아지지 않았다. 조종 연결도 같은 손실을 겪고 재전송을 기다리기 때문이다.

## 4. 서버

### 4.1 배포

`deploy/server/`의 docker compose로 zenohd와 fleetd를 함께 올린다.

```bash
cd deploy/server
cp env.example .env              # 공개 포트(TCP, UDP), fleetd용 로컬 포트, 경로
cp fleetd.example.yaml fleetd.yaml   # 차량 목록
docker compose up -d --build
```

- `.env`, `fleetd.yaml`, `data/`는 서버에만 둔다(`.gitignore`). 서버 주소와 포트는 저장소에 넣지 않는다.
- zenohd는 공개 TCP와 UDP 포트 외에 `127.0.0.1`의 포트를 하나 더 연다. fleetd는 이 포트로 붙는다.
- zenohd 설정(`zenohd.json5`)의 값은 다음과 같다. `max_links` 4는 차량 router가 TCP와 UDP를 함께 열 수 있게 하는 값이다. lease 1000 ms와 keep_alive 4는 tierlink의 `make_config`와 같다. 묶음 크기는 1400 B다.

### 4.2 fleetd

| 기능      | 동작                                                                                                                                                                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ack       | `<prefix>/monitor/data/*`의 메시지마다 `<prefix>/monitor/ack`로 ack를 보낸다. 차량의 monitor 조절기는 이 ack로 전송 속도를 정한다. 관제 프로그램은 monitor를 ack하지 않는다(`--ack-monitor`는 fleetd 없이 시험할 때 쓴다)                                     |
| 저장      | 차량별 폴더에 UTC 한 시간마다 MCAP 파일 하나(`<data>/<id>/YYYYMMDD-HH.mcap`)를 만든다. 채널은 차량의 ROS 토픽 이름, 메시지는 CDR, schema에는 타입 이름만 적는다. 그래서 `ros2 bag play`로 읽는다. 같은 시간에 다시 시작하면 `_2`를 붙여 앞 파일을 덮지 않는다 |
| 최근 기록 | `<prefix>/history/<stream>?seconds=N`에 답한다. 답 하나에 메시지마다 받은 시각(Unix ns, u64 LE), CDR 길이(u32 LE), CDR을 이어 붙인다. 메모리에 `history_seconds`만큼 둔다                                                                                     |
| 차량 목록 | `fleet/vehicles`에 JSON으로 답한다. 차량 ID, prefix, 차종, 지금 살아 있는 프로세스(`<prefix>/alive/*` 토큰)가 들어간다                                                                                                                                        |

- 타입을 모르는 스트림(catalog가 오기 전의 메시지)은 저장하지 않고, 종료할 때 개수를 로그에 남긴다.
- MCAP의 색인은 파일을 닫을 때 쓴다. fleetd는 SIGTERM을 받으면 파일을 닫고 끝난다(`docker compose stop`). 강제로 죽으면 그 시간의 파일에 색인이 없다.
- 데이터베이스는 쓰지 않는다. 외부 API가 없고 10대 규모라서, 차량 여러 대를 묶어 묻는 질의가 없다.

## 5. 엣지(차량)

- 차량 router는 `tierlink_edge`다. 차량 프로그램은 `tcp/127.0.0.1:7447`로 붙고, `tierlink_edge`가 서버와 `tcp/...?rel=1`, `udp/...?rel=0` 두 연결을 연다. UDP가 막힌 망에서는 UDP endpoint를 빼서 TCP만 쓴다.
- `tierlink_edge`는 링크 관리자도 겸한다. 차량의 Uplink가 100 ms마다 보낸 양, ack된 양, 지연을 `<prefix>/link/report/<tier>`로 보고한다. 링크 관리자는 이 보고로 차량 전체의 대역을 하나로 추정하고, 등급별 몫을 `<prefix>/link/budget/<tier>`로 100 ms마다 공지한다.

| 규칙               | 동작                                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 줄이기             | 지연이 100 ms를 넘으면, 실제로 ack된 양의 0.85배로 줄인다. 300 ms에 한 번까지                                                                                                         |
| 늘리기             | 지연이 30 ms 아래로 1초 이어지고, 보낸 양이 대역의 80% 이상일 때만 100 kbit/s 늘린다. 쓰지 않는 대역은 늘리지 않는다                                                                  |
| teleop 몫          | 대역에서 monitor 최소 몫(30 kbit/s)을 뺀 값을 150 kbit/s~2 Mbit/s로 자른다                                                                                                            |
| monitor 몫         | 나머지. teleop이 돌고 지연이 50 ms를 넘으면 최소 몫만 받는다. teleop이 없으면 대역 전체를 받는다                                                                                      |
| 계산에서 빼는 등급 | 3초 안에 ack가 한 번도 없었던 등급. 보는 관제가 없는 영상은 ack가 없어서 정지(stall)가 계속 커지는데, 이것을 혼잡으로 읽지 않기 위해서다. ack가 오다가 끊긴 것은 끊김으로 보고 줄인다 |
| 몫이 끊기면        | 각 프로그램은 500 ms 동안 몫을 못 받으면 자기 조절기(AIMD)로 돌아간다                                                                                                                 |

- 예전 방식(teleop_video가 텔레메트리 몫을 알려 주던 allowance)은 이것으로 대체했다.
- teleop_video의 영상 publisher와 관제 프로그램의 이동 명령(`motion`)은 best effort로 둔다. 나머지 제어 key(무장, 정지, 비상정지, 해제, 상태)는 reliable로 둔다.
- UDP에서 잃는 프레임을 다루는 방법은 정하지 않았다. 후보는 셋이다.
  - FEC: 패킷 몇 개마다 복구용 패킷을 더한다. 대역폭이 10~30% 늘어난다.
  - 인코더의 intra refresh: keyframe 대신 몇 프레임에 걸쳐 화면을 조금씩 새로 그린다. 프레임 크기가 고르게 된다.
  - 지금처럼 손실 뒤 keyframe을 요청하기.

  실제 영상으로 화면이 멈추는 시간을 재서 고른다.

## 6. 관제 프로그램

| 항목      | 설계                                                                 |
| --------- | -------------------------------------------------------------------- |
| 세션      | router 모드로 열고, 서버에 TCP와 UDP 두 연결을 연다                  |
| 첫 화면   | `fleet/vehicles`로 차량 목록과 접속 상태를 보여 준다                 |
| 조종 화면 | 차량 한 대를 고른다. 차량은 다른 세션의 무장을 거부한다              |
| 과거 기록 | fleetd의 `history` 조회로 받는다                                     |
| 비상정지  | `Link::estop()` 함수 하나로 둔다. 어떤 키에 연결할지는 정하지 않았다 |
